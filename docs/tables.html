Schema · one database, six academies

How tables are shared across tenants

There are 41 tenant-scoped tables and not one of them is named after an academy. Nothing is called raj_members. What varies between academies is the tenant_id in each row — never the table.

1The shape

Every row in every table carries which academy it belongs to. Row-level security is the only thing keeping them apart, so that column is load-bearing, not decoration.

The blind spot
attendance_roster(), attendance_history(), attendance_dashboard() and mark_attendance() read sessions + attendance_records only. They are listed in CLAUDE.md under "call these, do not reimplement" — which reads as a promise that they answer for every academy. They answer for Raj. Leo has 23 rows no shared function can see, and nothing said so, because nothing ever asked.
Why they were not merged
attendance_records requires a session and an enrolment, and a session requires a batch — all three columns are NOT NULL. Leo has 231 bookings and zero enrolments: it is a court venue, not a coaching academy. Its 23 rows cannot move into a model that demands a scheduled class they never had. They are not a broken copy of class attendance — they are a different fact, and forcing them together would have been the real bug.
Fixed today — migration 0041
The nouns are named. attendance.kind now accepts only 'staff' or 'member'; a fourth meaning is refused by the database instead of quietly accepted. Each table carries a written note saying what it holds and what it does not.

The blind spot is now watched. shared_fn_coverage() runs hourly and compares, per academy, the rows the shared functions can see against rows that exist where they do not read. Anything unreachable writes a warning to sync_log. Live right now: leo · 23 rows mpp ok raj ok

3The rule for the next academy

A new client arrives wanting something nobody has asked for before. Four questions, in order. Stop at the first one that fits.

Does the platform already have this thing, meaning the same thing? Not the same word — whether one sentence honestly describes both. "A member attended" and "a student was marked present in Tuesday's 6am batch" are not one sentence.
yes
Use the existing table.
Even if the client calls it something else — their word is a label, not a new noun. Never a new table.
e.g. Pride calls them "students", Raj calls them "members" → both are members.
Same thing, but they want to record an extra detail on it?
yes
A jsonb field on the existing table.
Not a new column, not a parallel table. Promote it to a real column only when a shared SQL function starts reading it, or a second academy needs it, or it needs a constraint or an index.
Why: the moment a shared function reads it, it has become platform vocabulary and deserves a proper column.
A genuinely new thing that only some academies will ever have?
yes
Its own tables — as a module.
Still tenant_id-scoped, still applied with --scope shared, switched on per academy via config.modules.X, with RLS and revoke … from public in the first migration, not a follow-up.
Done right: MatchPoint's 11-table player-tracking cluster. Copy that.
Same word as something we already have, but a different shape?
stop
This is the trap. Decide out loud before writing anything.
Two teams model the same-sounding thing two different ways, each inside their own repo, and nobody ever sees both. What you get is a shared function that silently answers for one academy and returns nothing for the others.
This is exactly what happened to attendance.
The one question to ask before any new table
Can one SQL function answer this for every academy that has the feature? If no, you have either the wrong table or the wrong noun — and you have to say which, out loud, before writing the migration.
Never
  • A table named after an academy — raj_enrollments. The tenant goes in a column.
  • A column on a shared table that only one academy uses. That is what tenants.config is for.
  • Two tables for one noun.
  • Shared DDL from a tenant's repo — even when it is correctly tenant-guarded. A trigger on members fires for all six academies; the guard makes it safe, not tenant-repo material.
