One schema, six academies

There are 41 tenant-scoped tables and not one is named after an academy. Nothing is called raj_members. What differs between academies is the tenant_id in each row — never the table.

1Who fills which table

Every table is shared; each academy simply uses the ones its business needs. Read down a column to see one academy's world, across a row to see how widely a table is used.

Where the differences actually live
Not in extra tables and not in extra columns. When one academy wants something slightly different — their UPI id, whether their timetable is public, which modules they bought — it goes in one jsonb settings bag on their tenants row: tenants.config. That is the whole mechanism.

The blind spot
attendance_roster(), attendance_history(), attendance_dashboard() and mark_attendance() read sessions + attendance_records only. They are listed in CLAUDE.md under "call these, do not reimplement" — which reads as a promise that they answer for every academy. They answer for Raj. Leo has 23 rows no shared function can see, and nothing said so, because nothing ever asked.
Why they were not merged
attendance_records requires a session and an enrolment, and a session requires a batch — all three NOT NULL. Leo has 231 bookings and zero enrolments: a court venue, not a coaching academy. Its 23 rows cannot move into a model demanding a scheduled class they never had. They are not a broken copy of class attendance — they are a different fact, and forcing them together would have been the real bug.
Fixed — migration 0041
The nouns are named. attendance.kind now accepts only 'staff' or 'member'; a fourth meaning is refused by the database instead of quietly accepted. Each table carries a written note saying what it holds and what it does not.

The blind spot is watched. shared_fn_coverage() runs hourly at :37 and compares, per academy, rows the shared functions can see against rows sitting where they do not read — anything unreachable warns to sync_log. Live now: leo · 23 unreachable mpp ok raj · 1,884 visible

3The rule for the next academy

A new client arrives wanting something nobody has asked for before. Four questions, in order. Stop at the first that fits.

Does the platform already have this thing, meaning the same thing? Not the same word — whether one sentence honestly describes both. "A member attended" and "a student was marked present in Tuesday's 6am batch" are not one sentence.
yes
Use the existing table.
Even if the client calls it something else — their word is a label, not a new noun.
e.g. Pride says "students", Raj says "members" → both are members.
Same thing, but they want to record an extra detail on it?
yes
A jsonb field on the existing table.
Not a new column, not a parallel table. Promote it to a real column only when a shared SQL function starts reading it, a second academy needs it, or it needs a constraint or an index.
Why: once a shared function reads it, it has become platform vocabulary and deserves a proper column.
A genuinely new thing only some academies will ever have?
yes
Its own tables — as a module.
Still tenant_id-scoped, still applied with --scope shared, switched on per academy via config.modules.X, with RLS and revoke … from public in the first migration, not a follow-up.
Done right: MatchPoint's 11-table player-tracking cluster — the tall violet column above.
Same word as something we already have, but a different shape?
stop
This is the trap. Decide out loud before writing anything.
Two teams model the same-sounding thing two ways, each inside their own repo, and nobody ever sees both. What you get is a shared function that silently answers for one academy and returns nothing for the others.
This is exactly what happened to attendance.
The one question to ask before any new table
Can one SQL function answer this for every academy that has the feature? If no, you have either the wrong table or the wrong noun — and you have to say which, out loud, before writing the migration.
Never
  • A table named after an academy — raj_enrollments. The tenant goes in a column.
  • A column on a shared table only one academy uses. That is what tenants.config is for.
  • Two tables for one noun.
  • Shared DDL from a tenant's repo — even correctly tenant-guarded. A trigger on members fires for all six academies; the guard makes it safe, not tenant-repo material.
